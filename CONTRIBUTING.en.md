# Contributing to GameScrcpy

[简体中文](CONTRIBUTING.md) · English

Thank you for helping! This guide covers reporting problems, setting up a development environment, building and testing, and the conventions to follow before you send code.

## Reporting problems and ideas

- Search the [Issues](https://github.com/NuoRan/GameScrcpy/issues) first.
- Use the bug report template: give the version, the Windows version, the phone model and Android version, the connection and the steps to reproduce, and attach the file made by "Settings > About > Export diagnostics".
- Do not open public issues for security problems; report them privately as described in [SECURITY.md](SECURITY.md).

## Sending changes

1. Fork the repository and branch off `main`.
2. Keep changes small and complete: one pull request does one thing and comes with its tests.
3. Build and run the relevant tests locally (see below); QML lint stays at zero warnings.
4. Write commit messages in English, with a first line of up to 72 characters that says what changed, and the reasons after a blank line when needed.
5. Open a pull request and fill in the template: what changed and how you verified it. Someone reviews it once CI passes.

For larger changes (new features, protocol or profile format changes), open an issue to discuss them first.

## Repository layout

| Path | Contents |
|:--|:--|
| `src/` | The Windows app in C++20 with Qt 6 / Qt Quick, and the `gs` command line (`src/cli`); modules are described in [docs/architecture.md](docs/architecture.md) |
| `android/` | Phone side: `protocol`, `server` (plain Java) and `companion` (the companion app, Kotlin) |
| `protocol/` | The protocol specification `SPEC.md`, the ESP32 protocol, and the golden test vectors shared by both sides |
| `sdk/` | Script API types and documentation generated by `gs api write`, and the C header for native extensions |
| `firmware/esp32/` | The ESP32 touch box firmware (ESP-IDF) and its built images |
| `tests/` | Unit, integration and interface tests, and test data |
| `examples/` | Sample components, tasks and extensions |
| `tools/` | Development and release scripts: environment, packaging, source rules, generators |
| `packaging/` | The installer script and the pinned adb version shipped with the app |
| `third_party/` | Third-party dependencies kept in the repository, listed in [third_party/README.md](third_party/README.md) |

## Development environment

| Tool | Version |
|:--|:--|
| Operating system | Windows 10 / 11 x64 |
| Visual Studio 2022 or later (MSVC) | With the "Desktop development with C++" workload |
| Qt | 6.10, the msvc2022_64 kit (with Qt Quick, Qt Quick Controls 2, Qt Shader Tools and Qt Test) |
| CMake | 3.28 or later, with Ninja |
| Python | 3.10 or later |
| JDK | 17 |
| Android SDK | Platforms 35 / 36, build-tools 35 / 36 |

Every dependency lives in `third_party/` and configuring never goes online; please do not add downloads such as FetchContent. FFmpeg, SDL3 and libusb are built from pinned sources and normally need no rebuild; see [third_party/README.md](third_party/README.md) for the steps.

## Building the Windows app

Point `GS_QT_DIR` at your Qt kit and load the development environment (once per terminal):

```powershell
$env:GS_QT_DIR = 'C:\Qt\6.10.1\msvc2022_64'
. .\tools\dev-env.ps1
cmake --workflow --preset msvc-debug
```

`tools/dev-env.ps1` loads the MSVC x64 environment, puts Qt on PATH and sets `JAVA_HOME` when it finds JDK 17. `cmake --workflow` configures, builds and runs the tests. The presets:

| Preset | Purpose |
|:--|:--|
| `core-only` | Builds and tests only the core libraries that do not need Qt |
| `msvc-debug` | The full Debug build |
| `msvc-release` | RelWithDebInfo with link-time optimization |
| `msvc-asan` | Debug with AddressSanitizer |
| `ci` | Like continuous integration: Release without link-time optimization, warnings as errors, without the tests that need a graphics card, a desktop or a phone |

Outputs go to `build/<preset>/bin`: `GameScrcpy.exe`, `gs.exe` and the test programs.

## Building the Android side

Point `ANDROID_HOME` at the Android SDK, then:

```powershell
. .\tools\dev-env.ps1
cd android
.\gradlew.bat build
```

`gradlew build` compiles the protocol, server and companion modules and runs JUnit and lint (lint warnings are errors). The server stays plain Java, without Kotlin. Dependency versions live in `android/gradle/libs.versions.toml`.

Mirroring a real phone also needs the server APK: run `.\gradlew.bat :server:assembleRelease`, then build the Windows app again, which places it next to `GameScrcpy.exe` as `gs-server.apk`.

## Testing

- Each module has a doctest program (`gs_base_tests`, `gs_protocol_tests`, `gs_input_tests`, `gs_session_tests`, `gs_media_tests`, `gs_script_tests`, `gs_blueprint_tests`, `gs_app_tests` and more), and the interface has Qt Quick Tests (`gs_controls_tests`, `gs_blueprint_ui_tests`, `gs_tour_tests`); all run through CTest: `ctest --preset msvc-debug`, or `-R <regex>` for a few.
- QML lint must report zero warnings: `cmake --build --preset msvc-debug --target all_qmllint`.
- The protocol tests read every golden vector in `protocol/vectors/`; C++ and Java must both match byte for byte.
- A few tests such as `gs_app_smoke` and `gs_video_render_*` open windows and need a graphics card; the tests that need a phone (`gs_adb_device_tests`, `gs_session_device_tests`) run only when `GS_ADB_TEST_SERIAL` names a device and are skipped otherwise.
- The mirror window works without a phone: `GameScrcpy.exe --demo-device tests\data\video\emulator_h265.media` adds a demo device that loops a recorded picture.
- `ADR-NNNN` and `XXX-NNN` in test names are the numbers of the project's design records and acceptance items.

## Changing the protocol

1. Change `protocol/SPEC.md`.
2. Change `protocol/tools/gen_vectors.py` and run `python protocol/tools/gen_vectors.py` to regenerate the vectors.
3. Make the tests pass on both the C++ side (`src/protocol`) and the Java side (`android/protocol`).

Never edit the generated vectors by hand.

## Changing the script API

After changing the API table in `src/script/src/Api.cpp`, run `gs api write sdk` from the repository root with the freshly built `gs.exe` to regenerate `sdk/`. The CTest `gs_script_api_current` checks that `sdk/` matches the program.

## Interface text and translations

- Interface text is written in English in the code (`tr()` / `qsTr()`); Chinese lives only in `src/app/i18n/gamescrcpy_zh_CN.ts`.
- After adding or changing interface text, run `cmake --build --preset msvc-debug --target update_translations` and fill in the Chinese with Qt Linguist or a text editor. Every entry must be translated; `gs_source_rules` checks it.
- The built-in help lives in `src/app/help/`: `index.json` gives the order, names, icons and titles of the articles, with one Markdown file each under `en/` and `zh_CN/`; new articles go into the resource list in `src/app/CMakeLists.txt`. `gs_app_tests` checks that both languages are complete and that every `help:` link points to an existing article.

## Source rules

`python tools/check_source_rules.py` (also the CTest `gs_source_rules`) checks that:

- Product code never runs or parses human-readable command output such as `dumpsys` or `wm` (R5).
- Nothing synchronizes with fixed delays: no sleeps, no single-shot timers with a delay, no `postDelayed` (R9). Where the delay is the feature itself, the line carries `source-rule-allow R9: <reason>`.
- Nothing captures the screen with `CopyFromScreen`.
- Every user-facing string has its translation, and source strings are English.
- Controls in `src/ui/controls` take colors, sizes and durations only from the theme.
- Every QML `Text` declares its `textFormat`.

## Code conventions

- C++20, formatted by `.clang-format` and `.editorconfig`; identifiers and commit messages in English.
- Let the code speak for itself: the code base carries almost no comments, apart from a short description at the top of a file; explanations belong in the pull request or the documentation. The `source-rule-allow` marker above is the only note that must sit on the line.
- Interface colors, type sizes, spacing, corner radii and motion come from the theme module `src/ui/theme`, never as bare numbers.
- New features come with tests; a bug fix starts with a test that fails.

## Packaging a release

Build the server APK and the `msvc-release` preset first, then run:

```powershell
.\tools\package.ps1 -Smoke
```

It collects what a release needs from `build/msvc-release/bin` (no test programs or PDBs), adds the Visual C++ runtime from Visual Studio and the adb pinned in `packaging/adb.json` (downloaded once into `deps/adb` and checked against its SHA-256 and Google's signature), and writes the installer, the portable zip and the symbols zip to `dist/`. Before writing them it checks that every program and DLL in the package finds what it imports in the package or in Windows; `-Smoke` also starts `GameScrcpy.exe --smoke-test` from the package (a window opens).

The installer is compiled by Inno Setup 6 or 7 from `packaging/GameScrcpy.iss`; the script looks for `ISCC.exe` in `GS_ISCC`, on PATH and in the usual install folders, and `-NoSetup` skips the installer when it is missing.
