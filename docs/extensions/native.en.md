# Native guide

[简体中文](native.md) · English

A native extension is a Windows DLL written in C or C++ that talks to GameScrcpy through the interface of [`sdk/include/gamescrcpy_ext.h`](../../sdk/include/gamescrcpy_ext.h). Use it to reach hardware directly, to handle touches fast on every frame, or to add new kinds of devices and connections to the program; for drawing interfaces and calling the existing APIs, [logic](logic.en.md) is simpler and does not ask the user to trust you fully.

The header is generated by `gs api write sdk` from the interface tables in the program, and describes every struct, field and function; this page shows how they fit together. It covers interface version `GS_EXT_ABI_VERSION` 2.

## The smallest DLL

```cpp
#include <gamescrcpy_ext.h>

#include <string>

namespace {

const gs_ext_host* g_host = nullptr;

int32_t greet(void*, const gs_ext_value* args, uint32_t, gs_ext_result* result)
{
    const std::string text = "Hello, " + std::string(args[0].text, args[0].size) + "!";
    return g_host->set_text(result, GS_EXT_TYPE_STRING, text.data(), text.size());
}

const uint32_t kGreetParams[] = {GS_EXT_TYPE_STRING};

const gs_ext_node kGreet = {sizeof(gs_ext_node), "greet", kGreetParams, 1, GS_EXT_TYPE_STRING, nullptr, &greet};

const gs_ext_contribution kContributions[] = {
    {sizeof(gs_ext_contribution), GS_EXT_KIND_NODE, "greet", &kGreet},
};

const gs_ext_plugin kPlugin = {sizeof(gs_ext_plugin), GS_EXT_ABI_VERSION, nullptr, 1, kContributions};

}

GS_EXT_EXPORT int32_t gs_ext_main(const gs_ext_host* host, const gs_ext_plugin** plugin)
{
    if (host == nullptr || plugin == nullptr || host->abi_version != GS_EXT_ABI_VERSION) {
        return GS_EXT_UNSUPPORTED;
    }
    g_host = host;
    *plugin = &kPlugin;
    return GS_EXT_OK;
}
```

The manifest says the same:

```json
"requires": { "native": "^2.0" },
"contributes": {
  "native": {
    "dll": "native.dll",
    "nodes": [ { "name": "greet", "params": [ { "name": "name", "type": "string" } ], "returns": "string",
                 "description": "Says hello to a name." } ]
  }
}
```

Logic calls it as `ext.alice.hello.greet("world")` (each part of the extension id in lowerCamelCase: `alice.lap-timer` becomes `ext.alice.lapTimer`).

## The entry point and the size of structs

- The DLL exports `gs_ext_main`. GameScrcpy calls it once after loading the DLL, with the host function table `gs_ext_host`; the DLL hands back a pointer to its own description, `gs_ext_plugin`. The DLL keeps that description and everything it points to valid until `unload` is called; GameScrcpy never writes to it.
- A DLL that only exports the old entry `gs_ext_entry` (interface version 1) is not loaded: interface 1 belongs to `native` 1.0, and 2.1 offers only 2.0. Build such a DLL again with the current SDK and write `"native": "^2.0"` in its manifest.
- Every struct that a DLL fills in, or that holds arrays, starts with `uint32_t size`, set to its `sizeof`. Each side reads only the fields both know and takes the others as 0, so later versions only add fields at the end of structs, and new DLLs work with older programs as old DLLs do with newer ones. The structs that are elements of arrays (`gs_ext_value`, `gs_ext_contact` and the like) are marked as never changing and have no `size`.
- Before using a host function that a later version added, ask `supports("<feature>")`. The features 2.1.0 knows: `jobs`, `events`, `settings`, `claims`, `job-output`, `app-events`, `input-sources`, `services`, `transports`, `media`, `frame-taps`, `vision-engines`, `devices`.

## The contribution table

`gs_ext_plugin.contributions` is an array (up to 256) of `gs_ext_contribution { size, kind, name, data }`: `kind` is a string, `data` points to the struct of that kind, and `name`, like the `name` in the struct, matches the name in the manifest. A `kind` that GameScrcpy does not know is logged and skipped, and the DLL still loads; what the manifest declares and the DLL lacks is shown on the Extensions page.

| `kind` | Constant | Struct | Manifest |
|:--|:--|:--|:--|
| `touch-method` | `GS_EXT_KIND_TOUCH_METHOD` | `gs_ext_touch_method` | `touchMethods` |
| `node` | `GS_EXT_KIND_NODE` | `gs_ext_node` | `nodes` |
| `attachment` | `GS_EXT_KIND_ATTACHMENT` | `gs_ext_attachment` | `attachments` |
| `behavior` | `GS_EXT_KIND_BEHAVIOR` | `gs_ext_behavior` | `behaviors` |
| `job` | `GS_EXT_KIND_JOB` | `gs_ext_job` | `jobs` |
| `device-provider` | `GS_EXT_KIND_DEVICE_PROVIDER` | `gs_ext_device_provider` | `deviceProviders` |
| `input-source` | `GS_EXT_KIND_INPUT_SOURCE` | `gs_ext_input_source` | `inputSources` |
| `transport` | `GS_EXT_KIND_TRANSPORT` | `gs_ext_transport` | `transports` |
| `video-source` | `GS_EXT_KIND_VIDEO_SOURCE` | `gs_ext_video_source` | `videoSources` |
| `audio-source` | `GS_EXT_KIND_AUDIO_SOURCE` | `gs_ext_audio_source` | `audioSources` |
| `media-sink` | `GS_EXT_KIND_MEDIA_SINK` | `gs_ext_media_sink` | `mediaSinks` |
| `recording-exporter` | `GS_EXT_KIND_RECORDING_EXPORTER` | `gs_ext_recording_exporter` | `recordingExporters` |
| `frame-tap` | `GS_EXT_KIND_FRAME_TAP` | `gs_ext_frame_tap` | `frameTaps` |
| `vision-engine` | `GS_EXT_KIND_VISION_ENGINE` | `gs_ext_vision_engine` | `visionEngines` |

Speech engines and AI providers have no kind of their own: the manifest builds them from jobs and nodes (see [Speech engines](#speech-engines) and [AI providers](#ai-providers)). The plugin description has five optional callbacks besides: `unload` (called once before unloading), `settings_changed`, `claim_wanted`, `on_event` and `device_event`; leave the ones you do not need `NULL`.

## Host functions

| Functions | For |
|:--|:--|
| `log`, `now_us` | Writing to the program log; a clock in microseconds that only goes forward |
| `store_get`, `store_set` | A store that outlives the program, up to 1 MiB of JSON in all, each value nested at most 64 levels deep |
| `allowed`, `notify` | Whether the user allowed a permission; showing a system notification (needs `notify`) |
| `set_text`, `set_error` | A node putting a text result or the reason it failed into `gs_ext_result` |
| `supports` | Whether GameScrcpy has a feature added later |
| `job_progress`, `job_log`, `job_finish`, `job_fail`, `job_output` | A job telling how far it got, logging, ending, and handing over part of its result while it runs |
| `emit_event` | Sending events to the extension's own logic and panels (and to the logic of the extensions that depend on it) |
| `events_subscribe` | Subscribing to GameScrcpy's program events, which come to `on_event` |
| `setting_get` | Reading the extension's settings |
| `devices_changed` | Having the Devices page list the devices of a provider again |
| `claim`, `release` | Claiming hardware and letting it go |
| `input_event` | Feeding the buttons and axes of an input source into the key mapping |
| `call_service` | Calling a service of another extension |
| `transport_changed`, `stream_opened`, `stream_data`, `stream_writable`, `stream_closed` | Transports |
| `sources_changed`, `video_frame`, `audio_samples`, `stream_ended` | Picture and sound sources |
| `device_list`, `device_open`, `device_write`, `device_control`, `device_close` | Using the devices the user allows, through GameScrcpy |

Strings are UTF-8 with a length, not ended by a zero byte (except where a struct says "ended by a zero byte"). The results are `gs_ext_status` values: `GS_EXT_OK`, `GS_EXT_FAILED`, `GS_EXT_UNSUPPORTED`, `GS_EXT_DENIED` (a permission is missing), `GS_EXT_BAD_ARGUMENT` and `GS_EXT_BUSY`.

## Threads and time

GameScrcpy calls the DLL on different threads, and each kind of callback has its rules:

| Callback | Rule |
|:--|:--|
| A node's `call` | The nodes of one DLL are called one at a time and return within 100 ms; they may come while touch methods work |
| A touch method's `open` / `close` / `frame` / `key`… | One thread at a time; `frame` runs on a time-critical thread and returns at once |
| The callbacks of attachments and behaviors | One at a time for each state, on a time-critical thread, never waiting; 2 ms for each call in its own process; three failures within 10 seconds turn the whole extension off |
| A job's `start` | Returns at once; the work happens on the DLL's own thread |
| A device provider's `list` | Returns within 100 ms |
| `settings_changed` | On a GameScrcpy thread (the interface thread in process, the message thread in its own process) |
| `claim_wanted` | Answers within a second |
| `on_event` | One event at a time, in order, on a thread that never draws the interface; return quickly, since more than 256 waiting are dropped |
| `call_service`, `claim` with `GS_EXT_CLAIM_WAIT` | Only from a job or the DLL's own thread, never from a node, an action, a touch method, an attachment, a behavior, a job's `start` or a callback |
| `device_list`, `device_open`, `device_write`, `device_control` | Only from the DLL's own thread, waiting at most 20 seconds; on GameScrcpy's threads they return `GS_EXT_UNSUPPORTED` |
| `device_event` | One event at a time, in the order the devices sent them, on a thread that never draws the interface; return quickly, since more than 1024 waiting are dropped |
| A recognition engine's `run` | On a thread GameScrcpy opens for it that never draws the interface, one picture at a time for each engine; after 5 seconds the logic gets an error, and the next picture comes only after it returns |
| `input_event`, `emit_event`, `job_*`, `device_close` | From any thread |

## Which process it runs in

Every DLL runs in a `gs-exthost.exe` process of its own, which GameScrcpy talks to through a shared-memory channel (only official extensions that ship with the program, with ids that start with `gamescrcpy.`, would be loaded into GameScrcpy's own process, and 2.1 has none). The separate process comes with these rules:

- A node call without an answer for 2 seconds, or a broken channel, ends the process, and the Extensions page says it did not answer in time.
- When the process stops unexpectedly, GameScrcpy writes a crash report (a minidump and `crash.txt`, which names the faulting module and offset) and records it in the extension's health; three stops within a minute turn the extension off until the user turns it on again.
- By default (`"sandbox": "full"`) the process runs with the user's rights; it is not a sandbox. A DLL can do whatever the user can, which is why it goes through the virus scan and the check of its imports before it is installed. With `"sandbox": "restricted"` in the manifest it runs in a sandbox; see [Restricted mode](#restricted-mode).

During development, `gs ext test <folder> --hosted` runs the tests in the separate process too (see [Testing extensions](testing.en.md)).

## System nodes

`gs_ext_node { size, name, params, param_count, returns, context, call }`: `params` holds the `gs_ext_type` of each parameter, in the order of the manifest. `call` gets arguments whose types were already checked; it puts the result into `result->value` (texts with `set_text`) and returns `GS_EXT_OK`, or calls `set_error` with the reason and returns `GS_EXT_FAILED`, which the logic gets as `GS-API-062` with that reason. The permissions a node needs go into `nodes[].permissions` of the manifest; without them the logic gets `GS-API-063` and the DLL is not called.

## Touch methods

A `gs_ext_touch_method` is offered under Touch method in Settings, after Normal, UHID and AOA. `open` gets a `gs_ext_touch_open`: the phone's serial and options as JSON, `{ settings, deviceSettings, phone, device, touchBox }`, holding the extension's settings for all phones, this phone's own settings, the phone id for `setting_get`, the USB, serial or Bluetooth device the user picked for it (`{ kind, path, name }` when the manifest says `wantsDevice`, otherwise `null`) and the device id when control started from a touch box card or a capture card is paired with the box (otherwise `null`). `frame` gets one frame of contacts (each position both as a ratio of the picture and as a ratio of the phone in its natural orientation); `key`, `text`, `mouse` and `gamepad` may be `NULL` to leave them to the normal way. Anything but `GS_EXT_OK` sends touches back to the normal way.

## Attachments and behaviors

- An **attachment** (`gs_ext_attachment`) hangs on a component: `input` changes, adds or swallows input before the component sees it, `output` changes, delays, adds or drops finger commands before they reach the phone, and `wake` hands over what was delayed once its time has come. `start` gets the parameters as JSON (the values of the manifest's `params`, plus the component's place `@position` and the picture's short-side unit `@unit`) and a seed: the same input must give the same output, so the seed is the only randomness to use.
- A **behavior** (`gs_ext_behavior`) is a new kind of component in the Extensions group of the component library: the manifest declares its input slots and parameters, `input` gets the events of the slots, and `frame` (at the pace of input shaping when `wants_frames` is 1) and `wake` give finger commands.

Both are called on time-critical threads: never wait, and do no file or network work there.

## Jobs

```cpp
int32_t flashStart(void* context, uint64_t job, const char* args, size_t size);
void flashCancel(void* context, uint64_t job);

const gs_ext_job kFlash = {sizeof(gs_ext_job), "flash", nullptr, &flashStart, &flashCancel};
```

- `start(context, job, args, size)`: `job` is the job's number and `args` a JSON object that matches the manifest's `params`. Return `GS_EXT_OK` at once and do the work on your own thread; anything else means the job did not start, and nothing more may be said about it.
- Tell how far it got with `job_progress(context, job, 0 to 1 or -1, text)` (passed on at most 20 times a second) and log with `job_log`; end with **exactly one** `job_finish(context, job, result JSON)` or `job_fail(context, job, reason)`. The result is at most 252 KiB and must match the manifest's `returns`; without `returns` the logic gets `null`.
- `job_output(context, job, JSON)` hands over part of the result while the job runs (such as each device a scan finds), up to 100 times a second; the logic hears it with `job.onOutput()`. Ask `supports("job-output")` first.
- `cancel(context, job)` asks the job to stop soon; it still ends with `job_fail` (or `job_finish` when it was done already). When the extension is turned off or replaced, or the program quits, GameScrcpy cancels every job and stops waiting after 3 seconds.
- An extension runs at most 4 jobs at once, fewer when the manifest's `most` says so; beyond that the logic gets `GS-API-067`. A failed job is `GS-API-065` in logic, a cancelled one `GS-API-066`.

In logic:

```ts
const job = ext.alice.board.flash({ port: "COM9" });
job.onProgress((fraction, text) => log.info(Math.round(fraction * 100), text));
const result = await job.result;
```

In a blueprint a job is one block with progress, done and failed outputs. Actions on device cards can start jobs too (see [Device providers](#device-providers)).

## Events

`emit_event(context, topic, JSON)` sends an event to the extension's own logic and panels, and to the logic of the extensions that list it in `dependencies`:

- The topic is 1 to 64 bytes of lowercase letters, digits, `.` and `-`, and never starts with one of GameScrcpy's own prefixes (`device.`, `session.`, `profile.`, `app.`, `orientation.`, `recording.`, `window.`, `extension.`, `settings.`), so no extension speaks for the program.
- The JSON is at most 64 KiB; an empty string means `null`.
- Each topic passes on its first 100 events in a second at once; of the ones after that in the same second only the last is kept and sent when the second is over.
- The extension's own logic hears it with `events.on("board.added", …)`, an extension that depends on it with `events.on("alice.board:board.added", …)`.

## Program events

`events_subscribe(context, topic, 1)` subscribes to one of GameScrcpy's own topics and `0` stops it; the events come to `on_event(context, topic, JSON)`:

| Topic | Value | Permission |
|:--|:--|:--|
| `device.connected`, `device.disconnected` | `{ phone, name }` | `events.app` |
| `session.started`, `session.ended` | `{ phone, name }`, plus `failed` when it ends | `events.app` |
| `profile.applied` | `{ phone, name, profile, profileName }` | `events.app` |
| `app.foreground` | `{ phone, name, package, game }` | `events.app` |
| `orientation.changed` | `{ phone, name, rotation }` in quarter turns | `events.app` |
| `recording.started`, `recording.ended` | `{ phone, name, path }`, plus `durationMs` when it ends | `events.app` |
| `window.focused` | `{ phone, name, window: "mirror" or "grid", focused }` | `events.app` |
| `extension.enabled`, `extension.disabled` | `{ id, name, version }` | — |
| `settings.changed` | `{ keys, values, extension, device }`, only for the extension's own settings and the language and look settings | — |

A topic it does not know gives `GS_EXT_UNSUPPORTED`, a missing `events.app` gives `GS_EXT_DENIED`. Events are merged as above.

## Settings

The settings of the manifest's `settings` are read with `setting_get(context, key, phone, value)`, which puts the value as JSON text into `value`, valid until the same thread calls it again. An empty phone gives the value for all phones; the `phone` of a touch method's options gives that phone's own value of a setting with `scope` `device`, or the value for all phones when it has none. A key the manifest does not declare gives `GS_EXT_BAD_ARGUMENT`. After the user changes settings, GameScrcpy calls `settings_changed(context, JSON array of the changed keys)`, with only the keys whose values really changed.

## Device providers

`gs_ext_device_provider { size, name, context, list, act }` needs the permission `devices.provide`. `list` writes a JSON array (up to 64 devices) with `set_text`, each:

```json
{ "id": "board-30C6F7A1", "name": "Touch box", "kind": "touchBox",
  "summary": "Firmware 1.0.2 · phone on USB", "state": "ready", "stateText": "",
  "icon": "svg:icons/board.svg", "touchMethod": "box", "resource": "serial:COM9", "capture": true,
  "actions": [ { "id": "settings", "title": "Settings", "panel": "board" },
               { "id": "flash", "title": "Flash firmware", "job": "flash" },
               { "id": "disconnect", "title": "Disconnect" } ] }
```

| Field | Rule |
|:--|:--|
| `id`, `name` | Required, at most 64 bytes |
| `kind` | One of the manifest's `kinds`, for now `touchBox`: a box that touches a phone without showing its picture |
| `summary`, `stateText` | A line about the device and the words of its state, at most 200 bytes |
| `state` | `ready`, `busy`, `problem` or `offline`; `ready` when left out |
| `icon` | An icon name or `svg:<package path>` |
| `touchMethod` | One of the extension's touch methods; Control opens a window without a picture that touches through it, with the device id as `touchBox` in the touch options |
| `resource` | The hardware it talks through, named as for `claim`; while someone else holds it, the card says who is using it |
| `capture` | `true` when a capture card may show its picture: while the box is connected it is offered under Touch method in the capture card's settings, and once chosen the capture card touches through `touchMethod`, again with the device id as `touchBox` |
| `actions` | Up to 8 buttons: `panel` opens one of the extension's panels (with `where` `device`), `job` starts one of its jobs, and those with neither go to `act` |

The action with id `settings` is the card's settings button; the others go into the card's More menu. When the job has a string parameter `device`, the card passes the device id in it. Call `devices_changed(context, provider)` when the devices change, and GameScrcpy calls `list` again.

## Hardware claims

Before opening a serial port, a HID, Bluetooth or USB device, call `claim(context, resource, flags)`, and `release` when done. Resource names ignore case: `serial:COM9`, `ble:AA:BB:CC:DD:EE:FF`, `hid:` and the path CreateFile opens, `usb:<vid>:<pid>:<serial number>` in hexadecimal.

- When someone else holds it, `claim` returns `GS_EXT_BUSY`. With `GS_EXT_CLAIM_WAIT` the holder is asked first and, when it agrees, GameScrcpy waits up to 3 seconds for it to let go; that takes time, so use it only from a job or the DLL's own thread.
- When someone wants hardware the DLL holds, GameScrcpy calls `claim_wanted(context, resource, by)`: return `GS_EXT_OK` within a second and `release` within 3 seconds to let it go, or anything else to keep it. `NULL` keeps it.
- When the extension stops, everything it held is let go. The program's own AOA sessions use the same claims, and `hardware.claim` in logic is the same thing.

## Input sources

`inputSources` in the manifest declares the device and its slots (`button`, `axis`, `stick`), the contribution table lists a `gs_ext_input_source { size, name }`, and the permission `input.provide` is needed. When a button or axis changes, call `input_event(context, source, slot, x, y, time)`: a button gives `x` 1 when it goes down and 0 when it comes up, an axis `x` from -1 to 1, a stick `x` from -1 left to 1 right and `y` from -1 up to 1 down, and the time is in microseconds of `now_us`, or 0 for now. It can be called from any thread and returns at once; each source passes on at most 1000 events a second, except a slot going back to 0, which always passes.

Profiles bind the slots as `Ext.<extension id>.<source>.<slot>`, and while the key editor waits for a key, pressing the device's button records it. When the extension stops, its buttons come up and its axes go back to 0.

## Services

`call_service(context, "<extension id>/<service>", JSON arguments, result)` calls a service that another extension offers in `contributes.services` and waits at most 10 seconds. On success `result` holds the result as JSON; otherwise it holds the reason: `GS_EXT_UNSUPPORTED` (no extension that is on offers it, or it was called on a GameScrcpy thread), `GS_EXT_DENIED` (the extension does not list the other one in `dependencies`), `GS_EXT_BAD_ARGUMENT` (the arguments or the result do not match the other side's schemas), `GS_EXT_FAILED` (the service failed or took too long). Call it only from the DLL's own threads, and ask `supports("services")` first.

To answer a service in the DLL, point the service's `node` at a node with one `json` parameter that returns `json`; it gets `{ caller, permissions, input }`: the id of the calling extension (an empty string for the user's own logic), the permissions both extensions have, and the arguments. `allowed()` only answers for this extension, so decide from `permissions` what to do for the caller.

## Speech engines

A speech engine is built in the manifest from jobs and a node; its id is `<extension id>/<name>`, it is offered in Settings › Audio › "Reading aloud and voice commands", and the logic's `speech.*` can pick it:

```json
"speechEngines": [ { "name": "cloud", "title": "Cloud voice", "say": "speak", "voices": "voices",
                     "listen": "hear", "dictation": false, "languages": ["en-US", "zh-CN"] } ]
```

- The `say` job takes exactly `text` (string), `voice` (string, empty for the default), `rate` (number, 0.5 to 2) and `volume` (number, 0 to 1); it ends once the text has been read and stops when cancelled.
- The `listen` job takes exactly `phrases` (json: an array of strings, or `null` when it takes any words), `language` (string) and `confidence` (number); it runs until it is cancelled and hands over `{ phrase, text, confidence }` with `job_output` for each command it hears.
- The `voices` node takes no parameters and returns a json array `[{ id, name, language }]`.

The manifest check makes sure these jobs and the node exist and take the right parameters (`speech-engine-invalid`).

## Transports

A `gs_ext_transport` adds a way to reach phones (a relay server, a tunnel, a cloud phone, another way of finding phones); it needs the permission `transport`, and `network` too when it uses the network:

- `discover` writes the phones it can reach now, `[{ id, name, model, detail }]`, with `set_text` within 100 ms; call `transport_changed` when they change. These phones appear on the Devices page with the transport as their connection.
- Each channel of a session (`control` first, then `video`, `audio` and `bulk` as needed) needs a byte stream: `open(context, stream, gs_ext_stream_open*)` returns at once, then `stream_opened` says that bytes can flow, or `stream_closed` with a reason that they cannot, within 20 seconds. The stream has to reach the abstract socket that the session's server listens on on the phone (`gs_ext_stream_open.session` names it, with the session's token and how GameScrcpy starts that server over adb); starting the server on the phone is the transport's business. GameScrcpy runs the normal session protocol over the stream, so encryption, authentication and the video coding stay the same.
- `send` takes at most 64 KiB at a time: `GS_EXT_OK` takes all of it, `GS_EXT_BUSY` none, and GameScrcpy sends again after `stream_writable`. Bytes from the phone go up in order with `stream_data`.
- When a stream ends (also when the phone closed its end), call `stream_closed`; the session sees a lost connection and tries to resume. GameScrcpy calls `close` when it is done with a stream.

Ask `supports("transports")` first.

## Pictures, sound and media outputs

These need the permission `media.capture` (sources) or `media.output` (outputs and exporters). Ask `supports("media")` first.

- **Picture sources** (`gs_ext_video_source`): `list` writes the pictures that can be opened, `[{ id, name }]`, which appear on the Devices page like capture cards; `open(context, id, params, stream)` returns at once, and the DLL then hands frames to `video_frame(context, stream, gs_ext_video_frame*)` from its own thread (`GS_EXT_PIXEL_BGRA` or `GS_EXT_PIXEL_NV12`, 2 to 4096 pixels, times on the clock of `now_us`); GameScrcpy copies them into a ring of a few frames and shows the newest. `stream_ended` says why a source stopped, such as an unplugged device; `sources_changed` asks GameScrcpy to list again.
- **Sound sources** (`gs_ext_audio_source`): the same `list` / `open` / `close`, with `audio_samples` handing over 48 kHz PCM, 16-bit or float, 1 to 8 channels. It plays with the extension's picture of the same id.
- **Media sinks** (`gs_ext_media_sink`): the user sends a mirror window here from the window's More menu (a virtual camera, a stream, OBS and the like). `open` gets the phone, the size and the formats, `frame` gets BGRA frames letterboxed into the manifest's size, and `audio` gets the sound; copy and return at once, and free everything in `close`.
- **Recording exporters** (`gs_ext_recording_exporter`): another format under Export as in the recordings list. `start(context, job, input MP4 path, output path)` converts on the DLL's own thread like a job, with `job_progress` and `job_finish` / `job_fail`; it counts as one of the extension's 4 jobs.

## Frame taps

A `gs_ext_frame_tap` reads the full-speed mirrored picture of each phone where the user turns it on in the mirror window's More menu; it needs the permission `media.read`, and `supports("frame-taps")` tells whether GameScrcpy has it. `open` gets the phone, the size and the rotation (a turned or resized picture closes the tap and opens it again); `frame` gets read-only BGRA frames (the long side made smaller to the manifest's `size`, at most the manifest's `fps` a second) on a thread GameScrcpy keeps for the tap, and may take its time: meanwhile only the newest frame waits. `frame` can put up to 256 shapes (rectangles, lines, points and text in a few theme colors) into the `gs_ext_overlay` to draw over the picture; the shapes of each frame replace the previous ones, and `keep` set to 1 leaves them as they were.

For a few frames a second in logic, use `media.frames` (see the [logic guide](logic.en.md)).

## Devices through GameScrcpy

`device_list`, `device_open`, `device_write`, `device_control` and `device_close` let a DLL use, through GameScrcpy, the serial, HID and Bluetooth LE devices the user allowed the extension; they are the same as `hardware.*` in logic. The extension's logic asks the user to tick devices with `hardware.request` (from its panel, for example), and the user takes them back on the Extensions page. They need the permission `hardware`; ask `supports("devices")` first. A DLL in [restricted mode](#restricted-mode) reaches hardware only this way, and a DLL with full rights may use them as well.

- `device_list(context, devices)` writes the allowed devices as a JSON array `[{ id, kind, name, present }]`: `kind` is `serial`, `hid` or `ble`, and `present` tells whether it is connected now.
- `device_open(context, id, options, &device, answer)` opens one and gives its number; a serial device takes the options of `hardware.open` in logic (`{ baudRate, dataBits, parity, stopBits, flowControl, dtr, rts }`), other devices none. GameScrcpy also claims the device's hardware for the extension (see [Hardware claims](#hardware-claims)) and lets go when the device closes. `GS_EXT_DENIED` when there is no permission or the user did not allow the device, `GS_EXT_BAD_ARGUMENT` for options that are not possible, `GS_EXT_FAILED` when it is not connected, someone else uses it or it does not open; `answer` gets the reason. Opening a Bluetooth device can take seconds.
- `device_write(context, device, data, size, target, answer)` sends data and returns when the device took it: to a serial device as it is, at most 65536 bytes; to a HID device as an output report with `target` `{ "report": id }`, at most 4096 bytes; to a Bluetooth LE device as the new value of a characteristic with `target` `{ "service": uuid, "characteristic": uuid, "response": true }`, at most 512 bytes (with `response` false it does not wait for the device to confirm).
- `device_control(context, device, request, answer)` does the rest of what `hardware.control` does, with the request's `op` one of `signals` (DTR and RTS of a serial device), `sendFeature` / `getFeature` (feature reports of a HID device), `services` (the services and characteristics of a Bluetooth LE device), `read` (reads a characteristic) and `subscribe` (turns its notifications on or off); bytes are base64 text both ways.
- `device_close(context, device)` returns at once and may be called from any thread, also from `unload`; GameScrcpy closes the DLL's devices itself when the extension or its process stops.
- What a device sends comes to `device_event(context, gs_ext_device_event*)` of the plugin description: `GS_EXT_DEVICE_DATA` (bytes from a serial device), `GS_EXT_DEVICE_REPORT` (an input report of a HID device, `report` being its id), `GS_EXT_DEVICE_NOTIFY` (a Bluetooth LE characteristic it subscribed to changed, named by `service` and `characteristic`) and `GS_EXT_DEVICE_CLOSED` (the device closed by itself, with `reason` `removed`, `failed` or `forgotten`).
- `device_list`, `device_open`, `device_write` and `device_control` wait for GameScrcpy (at most 20 seconds), so call them only from a thread of the DLL's own; on GameScrcpy's threads they return `GS_EXT_UNSUPPORTED`. The texts they give stay valid until the same thread calls one of them again.

## Recognition engines

`gs_ext_vision_engine { size, name, kinds, context, run }` reads text (`ocr`), finds things (`detect`) and tells what the picture shows (`classify`) for `vision.recognize` in logic, next to the text recognition of Windows (engine id `system`); an extension's engine id is `<extension id>/<name>`. `visionEngines` in the manifest says what it recognizes and which languages it reads; `kinds` in the struct holds bits such as `1u << GS_EXT_VISION_OCR`, at least those the manifest names. A DLL offers at most 4. It needs no permission (the logic that asks for it needs `device.screen`); ask `supports("vision-engines")` first.

```cpp
int32_t readText(void* context, uint32_t kind, const gs_ext_image* image, const char* params, size_t size,
                 gs_ext_result* out);

const gs_ext_vision_engine kReader = {sizeof(gs_ext_vision_engine), "reader", 1u << GS_EXT_VISION_OCR, nullptr,
                                      &readText};
```

- `run(context, kind, image, params, size, out)` gets the part of the picture the logic asked for: `gs_ext_image` is BGRA (alpha always 255), 1 to 4096 pixels each way, with a `stride` of at least 4 × width, read-only and valid until `run` returns; in `gs-exthost.exe` it comes through read-only shared memory. `params` is the JSON object the logic passed (`{}` when it passed none).
- Put the result into `out` as a JSON array with `set_text` and return `GS_EXT_OK`: `ocr` lists `{ text, x, y, width, height, confidence }` for each piece of text, `detect` `{ label, x, y, width, height, confidence }` for each thing and `classify` `{ label, confidence }` for each class. `x` and `y` are the middle and `width` and `height` the size, as ratios of the image from 0 to 1, which GameScrcpy turns into ratios of the whole picture for the logic; `confidence` goes from 0 to 1. Return `GS_EXT_BAD_ARGUMENT` for params it does not take, or call `set_error` and return `GS_EXT_FAILED`.
- GameScrcpy calls it on a thread of its own that never draws the interface, one picture at a time for each engine, perhaps while nodes, jobs and other engines run. After 5 seconds the logic gets `GS-API-174`, and the engine takes the next picture only after it returns. The other errors in logic: `GS-API-170` (no such engine, or its extension is off), `GS-API-171` (it does not recognize this kind or language), `GS-API-172` (the arguments are not right), `GS-API-173` (the engine failed or its result is not a valid list).

In logic: `await vision.engine("alice.finder/reader").read(res.region("Chat"))`, or `vision.recognize("alice.finder/reader", "ocr", region, params)`.

## AI providers

An AI provider adds a model service to Settings › AI: the assistant and `ai.ask` in logic can use it, and the list of models and the options for thinking, thinking effort and long context follow what it says. It has no contribution kind of its own; the manifest builds it from a node and a job, and it needs the permission `ai.provide` (and `network` with the service's hosts when it uses the network):

```json
"aiProviders": [ { "name": "cloud", "title": "My model service", "models": "models", "chat": "chat" } ],
"nodes": [ { "name": "models", "returns": "json", "description": "The models this service offers." } ],
"jobs": [ { "name": "chat", "title": "Answer", "params": [ { "name": "request", "type": "json" } ], "returns": "json" } ]
```

- The `models` node takes no parameters and returns a JSON array of models (up to 256), each `{ id, name, traits }`: `id` is required (at most 256 characters), `name` defaults to `id`, and `traits` tells what it can do: `think` (it can think before answering), `alwaysThinks`, `efforts` (thinking efforts, some of `minimal`, `low`, `medium` and `high`), `thinkingEffort` (the effort matters only with thinking on) and `longContext`.
- The `chat` job starts once for each question, and its parameter `request` is:

  ```json
  { "model": "…", "system": "…", "messages": [], "tools": [ { "name": "…", "description": "…", "inputSchema": {} } ],
    "stream": true, "maxTokens": 4096, "think": false, "effort": "", "longContext": false }
  ```

  `messages` holds, in turn, `{ "role": "user", "text", "pictures" }` (each picture `{ "type": "image", "mimeType", "data" }` with base64 `data`), `{ "role": "assistant", "text", "toolCalls": [ { id, name, arguments } ], "thinkingBlocks" }` and `{ "role": "tools", "toolResults": [ { id, name, failed, content } ] }`. When a request is over about 64 KiB, `request` becomes `{ "file": "<path>" }`: the same JSON in a temporary file, removed when the job ends (a restricted DLL can read it too).
- While answering, hand over pieces with `job_output` as `{ "text": "…" }`, `{ "thinking": "…" }` or `{ "toolCall": "<tool name>" }`, which the interface shows as they come; end with `job_finish` and `{ text, thinking, thinkingBlocks, toolCalls: [ { id, name, arguments } ], stop, usage: { input, output } }`, where a missing `text` or `thinking` is made of the pieces handed over. When the service fails, put `{ "problem": "…", "status": 429, "code": "…" }` into the result, or call `job_fail`.
- Two minutes without any output count as a failure; when the user cancels, GameScrcpy cancels the job. When the service chosen in Settings belongs to an extension that is not installed, is off or lacks `ai.provide`, `ai.ask` gets `GS-API-150`.

## Restricted mode

With `"sandbox": "restricted"` in `contributes.native`, the DLL runs in `gs-exthost.exe` inside an AppContainer of the extension's own. The interface is the same as for a DLL with full rights, but:

- **It cannot** read or write files outside the extension's folder (its own folder only reads), use the network or start other programs, and it sees only a few system variables, copied from GameScrcpy; what it can write is the extension's own container folder, `%LOCALAPPDATA%\Packages\GameScrcpy.Extension.<hash>\AC` and its `Temp`, while writes into the user's temporary folders are refused. Interface actions such as the clipboard, system settings and the windows of other programs are blocked too.
- **It can** reach hardware only through the [device functions](#devices-through-gamescrcpy) (with the permission `hardware` and the devices the user allows; `claim` needs `hardware` too); GameScrcpy hands it its store and the temporary files of AI requests.
- **Limits**: the process uses at most 1 GiB of memory and cannot start another process. GameScrcpy also limits it on its side: 200 log lines a second, 3 notifications in 10 seconds, 4 device changes a second and 16000 input events a second; what is over is dropped, with one line in the log the first time; the values of events must be valid UTF-8 JSON.
- The install check no longer asks for permissions that cover the network and file functions it imports; the install dialog says "Restricted: it can only do what it declares" and lists the system functions the sandbox blocks, and an unsigned package gets only a note.
- In `gs ext test` a restricted DLL always runs in `gs-exthost.exe` and an AppContainer too (made from `gs-test:<extension id>`, removed after the test), without `--hosted`.
- A known limit: the process in the container must be able to read and run `gs-exthost.exe` and the libraries next to it, so GameScrcpy grants that to "all application packages"; when those files belong to Administrators and GameScrcpy runs without elevation, it cannot change their permissions (error 5). That happens with a portable build unpacked to a drive other than the system drive by an elevated program; an installation under Program Files is not affected.

## One extension, several processors

The manifest's `dll` can be written as `{ "x64": "bin/x64/native.dll", "arm64": "bin/arm64/native.dll" }`: GameScrcpy loads the one for this computer's processor, and otherwise says that the extension has no version for this computer. `gs validate` checks each DLL's processor and that it exports `gs_ext_main`.

## Building

- Build an x64 DLL (and an arm64 one when you want) with Visual Studio 2022, include `gamescrcpy_ext.h` and export `gs_ext_main` (the header's `GS_EXT_EXPORT` is `__declspec(dllexport)`).
- Link the C/C++ runtime statically (`/MT`) so that the DLL does not depend on the runtime installed on the user's computer.
- `gs ext init native <folder>` writes a starting point that builds as it is: a CMake project, a copy of the header, a node, a job, a `contributes.cli` command and a test (see [Testing extensions](testing.en.md)).
- Ship the built DLL in the package; whether the sources go with it is up to you, and folders whose names start with a dot (such as `.build`) are never packed.
